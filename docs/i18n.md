# Localization (i18n)

Businesses can offer their content in more than one language. The common
case — a single-language business — is completely unaffected: everything
below is opt-in, additive, and invisible until a business declares more
than one `supportedLocales` entry. See
[adr/0008-per-business-bilingual-content.md](adr/0008-per-business-bilingual-content.md)
for why it's shaped this way.

## The two kinds of text on a page

1. **Business content** — a service name, a tagline, a testimonial quote.
   This comes from `static-data/` (soon: a backend) and is typed
   `LocalizableText` — see below.
2. **Platform chrome** — generic labels like "Our Services", "Send
   Message", a day name in the footer. This isn't business data; it's
   translated once, for the whole platform, via a small string dictionary.

Both resolve against the same current locale, but through different
mechanisms — don't conflate them.

## Business content: `LocalizableText`

```ts
export type SupportedLocale = 'en' | 'mr';
export interface LocalizedText {
  en?: string;
  mr?: string;
}
export type LocalizableText = string | LocalizedText;
```

(`packages/types/src/locale.ts`.) A content field typed `LocalizableText`
accepts either a plain string — what every existing single-language
business already uses, completely unchanged — or a `{ en, mr }` object.
Fields using this type: `Business.tagline`/`description`/`brandNote`,
`ServiceItem.name`/`description`, `GalleryItem.title`,
`Testimonial.quote`/`authorRole`, `SeoConfig.title`/`description`,
`SectionConfig.title`/`subtitle`, `FaqItem.question`/`answer`,
`TeamMember.role`/`bio`. Proper nouns (`displayName`, `legalName`,
`TeamMember.name`, `authorName`) are never localized — a business's actual
name doesn't change when a visitor switches language.

Resolve it with `resolveLocalizedText(value, locale)`
(`packages/utils/src/locale.ts`): a plain string passes through
untouched; an object resolves the requested locale, falling back to
English, then to whichever translation actually exists — a
partially-translated field never renders blank.

## Platform chrome: `translateUi`

`packages/utils/src/uiStrings.ts` holds a flat `{ en: {...}, mr: {...} }`
dictionary of generic labels (nav items, section title defaults, form
labels, button text) and one function, `translateUi(key, locale)`. This is
deliberately not a full i18n library — there's no pluralization or ICU
formatting need here, just "the same word in the other language." Where
word order genuinely differs (e.g. "About X" vs. "X विषयी" — the business
name moves), there's a dedicated function (`getAboutHeading`) instead of
forcing a template into the flat dictionary.

Day names and "Closed" also take a locale (`formatDayLabel`,
`formatHoursRange` in `packages/utils/src/formatters.ts`) for the same
reason — they're chrome around business data (`BusinessHours`), not
business data themselves.

## Choosing the current locale: `LocaleProvider`

`packages/providers/src/LocaleProvider.tsx` sits inside `BusinessProvider`
in `AppProviders` — it needs the resolved business to know
`business.supportedLocales` (first entry = default). It:

- Exposes `{ locale, availableLocales, setLocale }` via `LocaleContext`.
- Persists the choice in `localStorage`, namespaced per business
  (`rdplatforms:locale:<businessId>`), so a returning visitor keeps their
  language.
- Falls back to `['en']` for a business with no `supportedLocales` — the
  switcher (`packages/ui/src/layout/LanguageSwitcher.tsx`) renders nothing
  when `availableLocales.length < 2`.

Every component that needs the current locale calls `useLocale()`
(`packages/hooks/src/useLocale.ts`) — a thin wrapper over the context.

## Why resolution happens in components, not in services

`*Service` methods return the full bilingual object — they don't know
which locale is active. Resolution happens at render time
(`resolveLocalizedText`/`translateUi` calls inside section components),
not in the data layer, because switching language is instant and
client-side: it should never trigger a refetch. Every section component
calls `useLocale()` once per render and resolves whatever fields it needs
— never inside a loop callback (that would violate the Rules of Hooks);
`resolveLocalizedText` itself is a plain function, safe to call any number
of times per render, including inside `.map()`.

## Fonts: the gap this surfaced

`BusinessTheme.typography.fontFamily`/`headingFontFamily` were always just
name strings — nothing ever loaded them. For Latin fonts this was
invisible (a close-enough system font usually exists); Devanagari
(Marathi) made it obvious, since there's no reasonable fallback for a
display face like Yatra One. `typography.googleFontsUrl` plus
`loadGoogleFont()` (`packages/providers/src/theme/loadGoogleFont.ts`,
called from `AppThemeProvider`) fixes this generally, not just for
Marathi — see [DESIGN_SYSTEM.md](../DESIGN_SYSTEM.md).

## Fonts, part 2: a decorative heading font can break shaping for other scripts

Loading the right font (above) wasn't the whole problem. Swami Hair
Salon's `headingFontFamily` was `"'Yatra One', 'Noto Sans Devanagari',
serif"` — Yatra One is a Latin-only decorative face. Putting it first in
the stack didn't just fail to render Devanagari (that would be an obvious,
harmless fallback); it broke **shaping** for conjunct clusters like स्पा
or स्टा — visible stray halant marks, unjoined vowel signs — while
non-conjunct Devanagari text nearby looked fine. It only affected
headings, since only `headingFontFamily` (not the body `fontFamily`)
referenced Yatra One.

The fix: `ThemeTypography.headingFontFamilyByLocale` (`packages/types/src/theme.ts`)
lets a business override the heading font per locale.
`createAppTheme(businessTheme, locale)` now takes the current locale —
`AppThemeProvider` reads it via `useLocaleContext()` (it already sits
inside `LocaleProvider` in `AppProviders`) — and prefers
`headingFontFamilyByLocale[locale]` over the plain `headingFontFamily`
when present. Swami Hair Salon sets `headingFontFamilyByLocale.mr` to the
same Devanagari-safe stack as its body font, while English headings keep
Yatra One. Entirely opt-in: a business that never sets
`headingFontFamilyByLocale` behaves exactly as before. Unit tested in
`packages/providers/tests/createAppTheme.test.ts`.

**Lesson for the next display/decorative font pick:** verify it covers
every script a business's `supportedLocales` will actually render, not
just that the font "has some Unicode support" — partial coverage is worse
than no coverage, because it fails silently and only on specific
character clusters.

## Fonts, part 3: a decomposed vowel isn't the same as its precomposed letter

A third, unrelated bug in the same family: `uiStrings.ts`'s Marathi
"WhatsApp" strings were typed as अ (U+0905, the independent vowel letter
"a") followed by ॅ (U+0945, the candra-e vowel _sign_ — a dependent mark
meant to attach to a consonant's inherent vowel, as in बॅंक). That
combination has no defined glyph composition in most fonts, since ॅ isn't
designed to attach to another independent vowel letter — it rendered as a
broken/overlapping glyph. The correct Marathi spelling uses the single
precomposed letter ॲ (U+0972 DEVANAGARI LETTER CANDRA A), giving
व्हॉट्सॲप. Fixed in all four strings that had it
(`whatsappUs`, `sendViaWhatsApp`, `appointmentSentMessage`,
`contactSentMessage`).

This is a genuine spelling/encoding bug, not a font-coverage issue like
parts 1 and 2 above — Noto Sans Devanagari renders ॲ correctly. Worth
flagging if similar loanword spellings (candra vowels in word-initial
position) get added later: use the precomposed independent letter, not a
decomposed vowel-plus-matra sequence.

## Adding a language to a business

1. Add the locale to `Business.supportedLocales` (e.g. `['mr', 'en']` —
   first is default).
2. Fill in the new locale's key on every `LocalizableText` field that
   business uses.
3. If the script needs a font `fontFamily`/`headingFontFamily` doesn't
   already cover, update `typography.googleFontsUrl`. If a decorative
   `headingFontFamily` doesn't support that script, set
   `headingFontFamilyByLocale[locale]` to one that does (see above) rather
   than relying on the font stack's later entries — shaping doesn't fall
   back the way a missing glyph does.

No component changes — the switcher, resolution, and persistence are all
already generic.

## Adding a new UI-chrome string

Add the English value to `UI_STRINGS.en` in `uiStrings.ts` first (it's the
fallback for every locale), then the translation to `UI_STRINGS.mr`
(`satisfies Record<SupportedLocale, Record<string, string>>` means
TypeScript will error if a locale is missing a key). Call it with
`translateUi('yourKey', locale)`.

## Known limitation

The Marathi strings in `uiStrings.ts` and the demo business content in
`static-data/businesses/swami-hair-salon.json` are a reasonable first
pass, not verified by a native speaker — worth a review pass before this
is used for anything beyond internal development.
